# Boardcon SBC3576: preserved HAOS 18.5 port

This branch preserves the boot-corrected SBC3576 port from November 2026.
It adds a board target to Home Assistant **Operating System**, the Buildroot
distribution. Home Assistant Core and Supervisor application code was not
modified for the port.

## Source baseline

| Component | Exact baseline |
| --- | --- |
| HAOS | `18.5`, `fc301f556647b53281e853b9ce7f44915b3c7b14` |
| HAOS Buildroot submodule | `5c344b3789e3f6d620cf11ffab60e522a875cc79` |
| Rockchip Linux | `fee15752e3222f759d20871fff1e66989c3f1e88`, Linux 6.1.99 |
| Vendor SDK | `rk3576_linux6.1_sdk-20250623.tar.bz2` |
| Board target / image identifier | `sbc3576` |
| Supervisor machine / architecture | `qemuarm-64` / `aarch64` |
| Device tree | `rockchip/rk3576-evb1-v10-linux.dts` with the vendor patch |
| Wi-Fi | Vendor RTL8852BE PCIe module, built against the custom kernel |

The EVB-named DTS is not an assumption that every RK3576 board is equivalent.
The recovered SDK DTS compiled to the exact DTB read from the tested SBC3576:
`fa5585d12ddba06b70612219d65e1811a91d5d6293ae9f4b26b5a01669d87d2f`.
Other board revisions and peripheral combinations need their own verification.

## What changed in HAOS

The custom files are under `buildroot-external/board/boardcon/sbc3576`,
`buildroot-external/configs/sbc3576_defconfig`, and
`buildroot-external/package/sbc3576-rtl8852be`. The shared `Config.in` has
one additional package registration.

1. Select the Rockchip 6.1 kernel and apply the recovered vendor changes.
   Enable the HAOS requirements, including EROFS, AppArmor, cgroups,
   namespaces, overlayfs and dm-verity. Three board-local kernel patches
   contain the vendor changes, a 6.1 IPv6 reachability adaptation and a
   restriction to the one supported DTB build target.
2. Build the external RTL8852BE driver with the same toolchain and kernel.
3. Use the existing vendor boot chain. The U-Boot executable was **not rebuilt**
   during this port. The installation image includes SDK loader binaries;
   the tested eMMC installation instead preserved the board's working
   factory loader region. These are distinct bootloader provenances.
4. Store `Image` and `board.dtb` together in each 64 MiB FAT kernel slot.
   The old U-Boot lacks commands and filesystem support used by other HAOS
   targets. The boot script uses the commands actually available on it.
5. Implement A/B selection using a 32 KiB CRC-protected record in a dedicated bootstate partition,
   fixed partition positions checked against HAOS UUIDs, retry counters and
   RAUC's U-Boot backend. Each root filesystem slot is 512 MiB.
6. Correct the vendor legacy-script terminator and clear inherited DTB boot
   arguments before selecting the HAOS root partition. Both corrections were
   required during hardware bring-up; see the recovery document.

Common HAOS userspace patches remain referenced through relative symlinks in
the board's `patches/` directory. Kernel patches intended for HAOS's newer
6.18 kernel are not blindly applied to the 6.1 BSP.

## Scope of this branch

The board files match the archived, boot-corrected port baseline, with portable
documentation and tooling added. It does not include the household-specific
network guard added later. Its LAN exposure follows the base HAOS build; the
network isolation of the currently operated household system is an additional
deployment layer and must be restored separately on that installation.

The existing `qemuarm-64` Supervisor machine is reused for the container stack;
it does not mean this physical board is emulated. `sbc3576` is not in the
official HAOS update catalog. Do not install a generic-aarch64 or another
board's OS image as an update for this port. Core and app updates are separate
from replacing the custom host OS.

## Evidence and limits

| Item | Evidence |
| --- | --- |
| Kernel, DTB, Wi-Fi module and OS build | Completed; kernel embedded configuration checked |
| eMMC boot and automatic reboot | Verified on one SBC3576, with factory loader preserved |
| Docker, Supervisor and HA Core | Running; Core 2026.11.0 onboarding and device use verified later |
| Ethernet and Wi-Fi | Connected in the deployed system |
| Signed update and A/B slot boots | Verified later with the network-guard derivative; both A and B booted |
| Exact archived baseline image reflash | Not performed after final repackaging; structural checks passed |
| Power-loss recovery / deliberately failed update | Not tested on hardware |
| microSD boot and blank-board loader installation | Not tested |
| Camera on custom HAOS | Not tested; factory-OS camera results do not establish this |
| Long-term unattended reliability | Not established; one startup route-loss incident remains unexplained |

The artifact manifest distinguishes the baseline from the later guarded image.
The hashes are identities of preserved historical builds, not a promise of
bit-for-bit reproducibility from mutable package mirrors or a new signing key.
